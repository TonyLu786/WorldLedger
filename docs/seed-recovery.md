# Seed recovery

`worldledger seed` searches for world generation parameters consistent with structure placements you supply.

It is gated. It prints a responsibility notice in full and refuses to run until someone accepts it by name, and that name is written into every result file it produces. The gate is about attribution, not about safety: see [`trust-model.md`](trust-model.md), which explains why the exposure comes from publishing observations at all rather than from this tool existing.

## What is implemented

Structure placement, exactly.

Vanilla structures are placed by dividing the world into square regions and drawing one candidate chunk per region from a generator seeded from the world seed and the region coordinates. That generator is `LegacyRandomSource`, which is bit-compatible with `java.util.Random`, and it is still what Minecraft 26.2 uses:

```text
regionX = floorDiv(chunkX, spacing)
regionZ = floorDiv(chunkZ, spacing)
setSeed(regionX*341873128712 + regionZ*132897987541 + worldSeed + salt)
bound   = spacing - separation
chunk   = (regionX*spacing + evaluate(bound), regionZ*spacing + evaluate(bound))

evaluate = nextInt(bound)                              for linear spread
evaluate = (nextInt(bound) + nextInt(bound)) / 2       for triangular spread
```

Every constant was read out of the pinned 26.2 client jar, and `internal/seed` is checked against vectors generated by a real JVM (`internal/seed/testdata/`, produced by the `Gen.java` committed beside them). Changing those vectors requires explaining why the game changed.

## What is not implemented

Everything that would turn candidates into an answer.

- **The upper 16 bits.** Structure placement consumes only the low 48 bits of the seed. What the tool reports is a *structure seed*. Recovering the full 64-bit world seed requires biome or terrain evidence.
- **Biome and terrain generation.** Current releases run these on a different generator and a multi-noise pipeline. Modelling them bit-exactly is a separate undertaking of its own; nothing here approximates it.
- **Whether a structure actually generates.** A match means the placement algorithm *could* start a structure in that chunk. Biome and terrain conditions decide whether one does. So a mismatch disproves a seed, and a match does not prove one.
- **Structure detection.** Observations are supplied by the operator. The tool does not scan an archive and decide what it is looking at.

A run that finds nothing has not shown that no seed exists; it has shown that none was found in the range scanned. The result file reports the fraction of the space covered so that this cannot be misread.

## Worlds this cannot work on

- Servers using a hardened generator, where the seed is large or cryptographically derived.
- Servers whose generation is changed by a datapack, plugin, or fork, where the placement parameters in your input no longer describe the world.
- Worlds with no single scalar seed at all.

Placement parameters are inputs rather than built-in constants for this reason. Assuming vanilla values would produce confident wrong answers on exactly the worlds that are most likely to be modified.

## Input format

```json
{
  "schema": "worldledger.seed-observations/v1",
  "world": "a label for your own records",
  "observations": [
    {
      "placement": { "spacing": 32, "separation": 8, "salt": 14357617, "spread_type": "linear" },
      "chunk": { "x": 16, "z": 13 }
    }
  ]
}
```

`spacing`, `separation`, `salt` and `spread_type` come from the release's own worldgen data for the structure set you are using, not from this document.

## Use

```sh
worldledger seed --observations obs.json --operator you --accept-terms --seed 987654321
worldledger seed --observations obs.json --operator you --accept-terms --from 0 --to 100000000 --out result.json
```

The first tests one candidate. The second scans a closed range and reports how much of the space that covered, plus what a full scan would cost at the rate it achieved.

## Why brute force is not the technique

A single structure constrains weakly. Scanning 200,000 seeds against one observation leaves roughly 344 of them consistent, and at the rate this implementation achieves, covering the whole 48-bit space by brute force takes on the order of months on one core.

The real approaches constrain the search algebraically from the generator's structure instead of enumerating it, and the public seedfinding ecosystem has developed them in depth. This package deliberately implements the exact forward function and an honest scan rather than a weak imitation of that work: the forward function is what any constraint solver has to be correct against.

## Adding more evidence

More observations is what makes a search converge, not a wider range. Four structure placements already reduce a million-candidate scan to a single survivor. If a result reports more than one candidate, add constraints.
